# 集合竞价选股引擎

六组集合竞价条件，做成一个**盘中自动运行**的全市场选股引擎。全部走免费数据源，不需要 token、不需要开户。

**这个项目真正难的不是公式，是「数据只有一次机会」**：条件 1 需要 9:20 那一刻的累计竞价额，交易所不发布中间态，任何公开接口都查不到——抓不到就是当天作废。整个系统的架构都围绕这一个约束展开。

---

## 一、快速开始

```bash
# 1. 装依赖（本机已装的 pandas / requests 即可，无其他依赖）
pip install pandas requests

# 2. 盘前自检：确认数据源和链路正常（不用等 9:20 就能跑）
python selftest.py

# 3. 实盘：交易日 09:19 之前启动，脚本会自动等到 9:20 / 9:24 / 9:25 抓三次快照
python screener.py live
```

产出：
- 控制台打印**筛选漏斗**（每一层剩多少只）+ 命中明细表
- `output/选股结果_YYYYMMDD_HHMMSS.csv`（Excel 直接打开不乱码）
- `output/snapshots/YYYYMMDD/spot_*.json`（三次快照原件，可用于复盘）

## 二、六个条件 → 代码实现对照

| # | 条件 | 实现口径 | 数据来源 |
|---|---|---|---|
| 1 | 9:25竞价金额 / 9:20竞价金额 ＞ 12 倍 | 两次快照成交额之比 | 9:20 / 9:25 实时快照 |
| 2 | 9:25竞价价格 ≥ 9:24竞价价格 | 两次快照最新价比较 | 9:24 / 9:25 实时快照 |
| 3 | -1.5% ＜ 竞价涨跌幅 ＜ 6%；竞价金额 ＞ 350万 | `(9:25价/昨收-1)×100`；9:25 成交额 | 9:25 实时快照 |
| 4 | 3.5% ＜ 昨日换手 ＜ 20%；昨收 ＞ 60日均线 | 日K 换手率字段；昨收 vs MA60 | 日K（前复权） |
| 5 | 前30日有涨停；股价＜50；市值＜120亿；主板；非ST | 涨跌幅≥9.8%视为涨停；代码前缀判主板 | 日K + 快照 |
| 6 | 上上交易日涨跌幅＜6%；上上日成交额/昨日成交额＞110% | T-2 与 T-1 两根日K | 日K |

**执行顺序**（先便宜后昂贵，避免无谓请求）：

```
全市场 5900+
   ↓ 主板 & 非ST
   ↓ 竞价涨跌幅 -1.5%~6%
   ↓ 9:25竞价金额 > 350万                       ← 以上纯快照，零额外请求
   ↓ 股价 < 50元 · 流通市值 < 120亿
   ↓ 9:25/9:20 金额 > 12倍
   ↓ 9:25价 >= 9:24价
   ↓ 昨日换手率 3.5%~20%                        ← 以下需拉日K
   ↓ 昨收 > MA60
   ↓ 前30日有涨停
   ↓ T-2涨跌幅 < 6% · T-2/T-1成交额 > 110%
   ↓ 命中（通常个位数）
```

## 三、运行模式

v1.3 的主路径是**采样轨**，东财回算降级为兜底。

| 命令 | 用途 |
|---|---|
| `python runner.py` | **日常入口（推荐）**。按当前时间自动选路，不需要手动分辨模式 |
| `python runner.py --mode prep` | 收盘预筛：算条件4/5/6，产出次日候选池（定时 15:30） |
| `python runner.py --mode collect` | 强制采样轨：双源多轮采样 + 出结果（定时 09:19） |
| `python runner.py --mode resolve` | 强制定型轨：读已落盘采样重算，9:25 缺失用分时补（定时 09:31） |
| `python runner.py --mode backfill` | 东财回算（兜底，实测成功率 0~40%，不建议日常用） |
| `python runner.py --selftest` | 环境自检 |
| `python prep.py` | 预筛单独调用。`--for-date` 指定池子服务的交易日 |
| `python collector.py --dry` | 立刻采一轮候选池快照，验证链路 |
| `python backfill.py` | 东财回算单独调用 |
| `python screener.py probe --code 600000` | 打印单只股票字段，实盘对账用 |

### ★ 六个条件的数据可补性（v1.3 的架构依据）

这是理解 v1.3 为什么这样设计的关键。2026-10-19 逐个接口实测得到：

| 条件 | 需要的数据 | 能否事后补 | 依据 |
|---|---|---|---|
| 条件1 | 9:20 累计成交额 | **不能** | 交易所不发布竞价中间态，任何公开接口都查不到 |
| 条件2 | 9:24 竞价价 | 不能，但可邻近轮次顶替 | 同上；顶替后判定偏宽松 |
| 条件3 | 9:25 竞价价 + 竞价额 | **能** | 腾讯分时第一根盘后任意时刻可查，且逐位一致 |
| 条件4/5/6 | 历史指标 | 能 | T-1 15:30 预筛已算完 |

**结论：整个系统真正的脆弱点只有 9:20 那一次抓取。**

所以 v1.3 把资源重新分配（v1.2 是三窗口等权）：

```
v1.2：9:20 / 9:24 / 9:25 三窗口等权，各 10+ 轮
      → 9:25 那 45 秒是白费的（可后补），9:20 反而不够厚

v1.3：9:20  09:19:40–09:20:30  1.5s/轮 + 腾讯/新浪双源并行   ← 唯一硬约束
      9:24  09:23:40–09:24:30  2.0s/轮
      9:25  → 改成 09:25:00–09:29:50 的「静止窗」
             竞价已结束、连续竞价未开始，(价,量,额) 完全冻结，
             抓一轮即定，检测到定型就收工，不必挤在 45 秒里抢
```

**9:25 分时补数的实测依据**（2026-10-19，600354）：

```
分时第一根：  0930  8.31  4905  4076055.00
当天真实结果：open=8.31  竞价量=4905 手  竞价额=4076055 元   → 逐位一致
```

腾讯把 09:15–09:25 的竞价成交全部归到 09:30 这一根（09:31 起才是含连续
竞价的累计量），所以第一根 = 纯竞价结果。**这条通道让条件3 彻底不再依赖
9:25 那个时点。**

### 双源并行（v1.3）

| 源 | 接口 | 100 只耗时 | 与对方交叉核对 |
|---|---|---|---|
| 腾讯 | `qt.gtimg.cn` | 0.05~0.2s | 基准 |
| 新浪 | `hq.sinajs.cn` | 1.45s | 成交额相对差中位数 **0.0007%** |

每轮先打腾讯，失败立刻换新浪，**只在失败时才多花 1.4 秒**。
两个域名族历史上从未同时挂过。落盘文件名记录来源（`r0920_092003_sina.json`），
事后可复盘当天走的是哪条通道。

注意新浪这档**不给市值/换手率**，缺失的 `float_mv` 用预筛池的
`shares × 当日价` 补 —— 不补的话条件5 的市值过滤会把整批股票**静默剔除**。

### runner.py 的自动选路规则（v1.3）

```
现在时间
  ├ 09:25:45 之前 → 采样轨
  │    · 09:15 前启动   → 等到 09:19:40 开始
  │    · 09:20:30 后启动 → 9:20 窗口已过，结果标注「低置信度」
  └ 09:25:45 之后 → 定型轨
       · 有当天完整采样 → 直接读盘重算（几秒，不联网）
       · 缺 9:25        → 腾讯分时第一根补回，再走完整判定
       · 缺 9:20 / 9:24 → 输出「低置信度结果」，标注哪条没验证
       · 完全无数据      → 回退东财回算（兜底）
```

### 为什么放弃「三个时点各抓一次」

条件 1 要「9:20 的累计竞价量」、条件 2 要「9:24 的竞价价」，这两个数
**只有两个来源**：多时点快照，或东财 `details` 分笔明细。没有第三条路。

而东财 `details` 在 2026-10-19 实测已不可用：

| 通道 | 结果 |
|---|---|
| 走系统代理 | **0/3 全失败**（ProxyError），而腾讯/新浪走同一代理正常 |
| 绕过代理直连 | 26 次约 37%，且**持续衰减**：14:23 约 40% → 14:29 已 0/6 |
| 静默 4 小时后再测 | 仍然 `RemoteDisconnected` |

逐项排除过：不是本机断网（百度 2/2 通）、不是某个镜像域名坏（5 个域名全测）、
不是同码重复请求限流（6 只全新代码 0/6）、不是频率过高（间隔拉到 6 秒仍 33%）。

所以唯一出路是把快照采样做厚 + 做多源：

```
旧：09:20:02 / 09:24:02 / 09:25:06 各 1 次 → 任一失败当天作废
新：9:20/9:24 双源并行多轮 + 9:25 静止窗 → 任一轮成功即可，且每轮落盘
```

采样是**候选池级**的（1 批请求 ≈ 0.2s），不是全市场级（10 批）。候选池由
`prep.py` 在收盘后算好，通常 50~300 只。

### 三个定时任务

| 时间 | 任务 | 作用 | 依赖 |
|---|---|---|---|
| 15:30 | 预筛 | 用当日收盘日K算条件4/5/6 → 候选池落盘 | 东财/腾讯/新浪任一 |
| 09:19 | 采样 | 9:20/9:24 双源采集 + 9:25 静止窗 + 出结果 | 腾讯或新浪 |
| 09:31 | 定型 | 读落盘数据重算，9:25 缺失用分时补 | 仅分时补数时联网 |

定型轨从 09:26 后移到 **09:31**：采样轨的静止窗要到 09:29:50 才结束，
早了会两个进程抢同一个文件锁。

09:31 的定型轨**不重新采样**，因此它不会因为网络问题失败，也不会覆盖
09:19 的好结果 —— 它只是把同一份数据再算一遍作为保险。

安装任务时会同时设置 `WakeToRun`（睡眠自动唤醒）和 `StartWhenAvailable`
（错过就补跑）。关机无法唤醒（需要 BIOS 定时开机，普通用户不会配），
所以使用说明里仍要求「9:19 前处于开机或睡眠状态」。

## 五、⚠️ 关键口径与已知限制（必读）

**1. 竞价中间态（9:20 / 9:24）只有东财分笔能还原 —— 而它现在不可用。**

机制上确认：东财分笔明细 `/api/qt/stock/details/get?pos=-6000` **覆盖 09:15~09:25**，
每条形如 `09:20:06,9.73,413,0,4`，第 3 列是**累计竞价匹配量（手）**，单调递增到
09:25:00 的最终撮合量。所以三个时点从原理上都能精确还原
（600354 实测：9:20 = 321手×8.23 ≈ 26万、9:24 价 = 8.20、9:25 = 4905手×8.31 = 408万）。

但 2026-10-19 实测这条通道**已经挂了**：走系统代理 0/3 全失败，直连 37% 且持续衰减到 0，
静默 4 小时后仍是 `RemoteDisconnected`。腾讯分笔 `deal/query` 与新浪分笔
`CN_Bill.GetBillList` 都返回空，没有替代品。

所以现在的分工是：

| 数据 | 实时快照 | 事后补 | 结论 |
|---|---|---|---|
| 9:20 累计额（条件1） | ✓ 唯一途径 | ✗ 无 | **必须在 9:20 抓到** |
| 9:24 价（条件2） | ✓ 唯一途径 | ✗ 无 | 必须在 9:24 抓到，可用邻近轮顶替 |
| 9:25 价+额（条件3） | ✓ | ✓ 腾讯分时第一根 | 丢了也能补 |
| 历史指标（条件4/5/6） | — | ✓ T-1 预筛 | 不占早盘 |

抓不到时不再写「今日无股票」，而是输出**低置信度结果**并标注哪条未验证 ——
这是有意的产品决定：给出一份标注了可信度的参考结果，比让人空等一早上更诚实。

注意 09:15~09:25 之间明细里的成交量/额字段恒为 0（虚拟撮合），必须用累计量折算 ——
如果哪天东财恢复，这一条仍然适用。


**2. 「自由流通市值」用「流通市值」近似。**
免费接口给的是流通市值，拿不到自由流通市值。流通市值 ≥ 自由流通市值，所以这条**只会多筛不会漏**（比较宽松）。若要精确口径，需接 tushare 的 `daily_basic.free_share × close`（需积分）。

**3. 条件6 只设了上限，没有下限 —— 大跌股会一起通过。**
原文「上上个交易日涨跌幅 ＜ 6%」只限制上限。实测中 T-2 跌 5%~8% 的股票同样满足（如 -5.13%、-8.07%）。若本意是「T-2 是温和整理」，建议补下限（如 `> -3%`）—— 目前代码按条件原文严格执行，下限作为可选项留在 `config.json`。

**4. 涨停判定 = 日涨跌幅 ≥ 9.8%（主板 10% 制）。**
这是「收盘涨停」。若要「盘中触及过涨停」，把 `zt_threshold_pct` 调小即可。

**5. 涨跌幅按前复权价计算，除权日会失真。**
东财源的涨跌幅直接用交易所口径字段，准确。备用源（新浪/腾讯日K）用前复权收盘价做差分，若 30 日窗口内发生除权送转，涨停判定可能出现偏差（概率低，但存在）。

**6. 脚本会自检是否真的处在竞价时段。**
若首尾两次快照的成交额有 95% 以上完全相同，说明当前不是竞价时段（数据没在动），会直接打出警告 —— 避免你拿到一份看着像结果的废数据。

**7. 数据源：东财为主，腾讯+新浪为备，自动降级。**

| | 全市场快照 | 日K 字段 | 拉 50 只日K耗时 |
|---|---|---|---|
| 东财（主） | 60 页 × 100，约 20 秒 | 成交额 ✓ 换手率 ✓ 真实涨跌幅 ✓ | 约 10 秒 |
| 腾讯快照（备） | 10 批 × 600，约 18 秒 | — | — |
| 腾讯日K | — | OHLCV（额/换手需折算） | 约 3 秒 |
| 新浪日K（纯 HTTP） | — | OHLCV（额/换手需折算） | 约 5 秒 |

日K 三档降级：**东财 → 腾讯 → 新浪**。新浪那一档是纯 HTTP 实现，**不走 akshare**
（akshare 的 `stock_zh_a_daily` 依赖 py_mini_racer/V8，多线程会段错误）。

> 2026-10-19 交叉验证：用新浪日K 重算 600354 的已知指标，与东财/腾讯口径逐位一致
> —— MA60 7.797、T-2 涨跌幅 -6.17%、T2/T1 成交额比 1.182、近 30 日涨停日 2026-10-09。
>
> ⚠️ **但「三源口径可完全互换」这句话已被证伪**（同日实测，见下面第 9 条）：
> 腾讯走 **前复权**、新浪纯 HTTP 走 **不复权**，两者在含除息的 60 日窗口上算出的
> MA 不同，会让临界股翻转结论。600354 恰好离 MA 边界较远（+1.32%）所以一致，
> 换成临界股就露出来了。

备用源若只能退到腾讯/新浪日K（无真实换手率字段），换手率由**流通股本反推**
（`float_mv / price`），实测与真实值完全一致；成交额按量 × 四价均价估算 ——
相邻两日同法估算，比值误差可抵消。此时脚本会置 `degraded_history` 标记，**不会静默当精确值用**。

**8. 接口限流有三种形态，处理方式不同（2026-10-19 实测）。**

| 形态 | 表现 | 代码对策 |
|---|---|---|
| 东财「速率触发」★ | 冷却后**第一次**请求成功，紧接着连发就全断；同一网址 3 分钟内结果相反 | 全局节流 `em_throttle`：所有东财请求串行 + 间隔 ≥2s + 抖动 |
| 东财「半死」 | 能连通，但 60 页里 58 页取不到，只回来 200 只 | 失败页超 1/3 即抛错；快照 < 1000 只直接中止 |
| 腾讯「WAF 拦截」 | 日K 接口返回 **HTTP 501** 并跳 `waf.tencent.com` 验证页 | `WafBlocked` 异常不重试 + `TX_BREAKER` 熔断 180 秒 |

**第一种是 2026-10-19 新确认的**，也是过去一直误判的：它不是「封了某个接口」，
而是**按请求速率掐断**。实测证据——同一端点连续两个时间点结果完全相反：

```
14:11:20  单次请求（距上次约 3 分钟） -> HTTP 200 成功
14:11:36  紧接着连发 6 次，间隔 1 秒  -> 0/6 全断
```

社区口径（a-stock-data 防封文档 / efinance issue #208）：**>5 次/秒、单 IP 并发 ≥10、
1 分钟 ≥200 次、5 分钟 ≥300 次** 即触发；重度案例（1 小时 4.5 万请求）
**IP 封禁持续 20+ 小时**。

**我们改造前的调用量正好踩在线上**，这是「跑一次就再也跑不出来」的真正原因：

| 项 | 改造前 | 改造后 | 说明 |
|---|---|---|---|
| `page_sleep`（快照分页） | 0.06s ≈ **16.7 次/秒** | 0.5s（QPS 2） | 60 页约 30 秒，慢 20 秒换稳定 |
| `detail_retries`（单只重试） | **30 次** × 4 域名 | 3 次 | 45 只候选从上千次请求降到 ~50 次 |
| 明细并发 | 3~5 线程 | **串行**（`em_throttle` 强制） | 45 只 × 2s ≈ 90 秒，仍赶得上开盘 |
| 连续失败处理 | 逐只硬顶到底 | **连续 6 只即中止整轮** | 几十秒给出明确结论，不把 IP 打进冷却 |
| `EM_BREAKER` | 2 次失败 / 冷却 90s | **8 次 / 冷却 120s** | 原阈值太敏感，风控一抖就误判「接口全挂」 |

对应配置项（`config.json` 的 `_throttle` 段）：`detail_retries` /
`detail_max_consec_fail` / `em_min_interval`。**这三项调大就会招来封 IP，不要动。**

> 触发条件：同一台机器短时间内连续跑多次全市场（实测跑了 4 次全量后腾讯开始返回 501）。
> 每天跑 1 次不会触发。为降低风险，日K 已加**当日缓存**
> （`output/cache/kline_YYYYMMDD.json.gz`），同一天重跑不再重复请求。

**9. ★ 日K 复权口径：前复权 vs 不复权，会让临界股进/出池子（2026-10-19 实测）。**

三档日K的复权口径**并不统一**，这是 v1.2 才发现的问题：

| 源 | 复权口径 | 「昨收 > MA」是否正确 |
|---|---|---|
| 东财（主） | 前复权 `fqt=1` | ✓ |
| 腾讯日K | **前复权** `qfq` | ✓ |
| 新浪纯 HTTP | **不复权** | ✗ MA 偏高，判定偏保守 |

不复权序列在除息日会留下「价格缺口」，60 日 MA 因此被抬高，`昨收 > MA` 就被低估
——**恰好卡在均线附近的股票会被误剔除**。分红除息集中在 5~7 月，所以 7~10 月
（60 个交易日的回看窗口压在分红季上）受影响面最大。

同一份数据、同一套代码，只有日K源不同，实测结果：

| 日K源 | 换手率 | 昨收>MA | 近30日涨停 | 量价 | **候选池** |
|---|---|---|---|---|---|
| 前复权（腾讯） | 466 | **233** | **193** | **100** | **100 只** |
| 不复权（新浪） | 466 | 232 | 192 | 99 | 99 只 |

差异全部来自 **002972**：不复权 MA60 = 13.2068，昨收 13.190，差 **-0.127%** 不通过；
前复权下通过。已排除窗口偏移（shift -2/-1/0 三种对齐全部不通过）、
送转除权（130 天内无 >10% 跳空）、数据错误 —— 只剩复权口径这一个解释。

**已做的处理：**

1. **根因是并发过高把腾讯打进 WAF**。10 线程跑 2272 只 = 91 只/秒 → 腾讯返回
   HTTP 501 → 静默降级到新浪不复权 → 漏股。降到 **4 线程（约 31 只/秒）后腾讯全程
   不被拦**，2272 只耗时 74 秒（10 线程是 25 秒，但会漏股）。
   `prep.HIST_WORKERS_MAX = 4` 是**硬上限**，任何调用方传更大的并发都会被夹住。
2. **绝不静默降级**。每次预筛结束都会打印一行口径统计，
   并写入池子文件的 `kline_adj` 字段：

   ```
   日K复权口径：前复权 2272 只（正常）
   日K复权口径：[!] 全部为不复权 2272 只（腾讯日K 不可用，已降级） —— MA 判定偏保守，可能漏掉临界股
   ```

   看到带 `[!]` 的那行，说明这次池子可能少 1~2 只临界股。**当天重跑一次预筛即可**
   （腾讯冷却 180 秒后会恢复），不用改任何配置。

**尚未处理的：** 不复权这一档没有做复权修正（新浪的复权接口返回加密串、
akshare 的 qfq 依赖 py_mini_racer 不能多线程）。当前策略是「保证不走那一档」+
「走了就明说」，而不是硬修。真要彻底消除，需要引入分红除权数据自己算复权因子，
这是一个独立工作量。

### 一轮采样的落盘长什么样

`output/snapshots/20261020/rounds/r0925_092502_tx.json`：

```json
{
  "tag": "0925",
  "source": "tx",
  "captured_at": "2026-10-20 09:25:02",
  "count": 100,
  "rows": [{"code": "002181", "name": "粤传媒", "price": 9.59,
            "open": 9.59, "volume": 12996, "amount": 12463000.0, ...}]
}
```

`open` = 今开 = 集合竞价成交价，`volume`/`amount` = 该时刻的累计竞价量/额。
9:25 撮合完成前它们是虚拟撮合值，完成后就是最终竞价结果。

文件名尾部 `_tx` / `_sina` 是数据来源（v1.3 起）。旧版本文件没有这个后缀，
读取时按 `tx` 处理，向后兼容。

### 定型判定

9:25 的样本不能随便取 —— 撮合可能有几秒延迟。判定规则：

> 相邻两轮的 `(volume, amount)` 逐只完全相同（>98%）⇒ 撮合已完成、进入静止状态，
> 取这一对里的后者作为 9:25 终值。

若整个窗口都在变，退化为取最后一轮，并在结果里明确标注「未确认定型」——
宁可标出来，也不假装拿到了终值。

v1.3 起静止窗是 09:25:00–09:29:50（5 分钟），所以通常第 2 轮就能确认定型并
提前收工，不用把窗口跑满。**不确认定型的风险也随之降低**：原窗口只有 45 秒，
一旦撮合慢几秒就没有退路。

## 七、故障排查：某天为什么没有结果？（2026-10-19 补）

### 已修复的致命缺陷

**现象**：任务到点跑了，但没有结果、没有弹窗，日志里只有一行「启动」。

**根因**：`run_live()` 直接调用 `src.spot()`，**没有任何异常保护**。东财分页抓取时，只要任意一页请求失败（网络抖动 / 接口限流），就抛 `RuntimeError`；被 PyInstaller 顶层捕获后**进程直接退出**。而任务计划的窗口是关掉的，崩溃信息只打到 stderr —— 用户端什么都看不到。

**修复（四处）**：

| # | 修复 | 位置 |
|---|---|---|
| 1 | 抓取容错：主源失败**自动降级**备用源（腾讯+新浪） | `_grab_spot()` |
| 2 | 三源全失败也写 `最新结果.txt`（显示失败原因），不再让人看到旧结果或空白 | `write_fail()` |
| 3 | 全局兜底：捕获所有未处理异常，traceback 写入 `logs` 和 `最新结果.txt` | `main()` |
| 4 | 任务入口把 exe 的 stdout/stderr 追加到 `output/logs/task_collect.log` | `_定时任务入口.bat` |

### 自助排查

双击 **`6-诊断定时任务.bat`**，会生成并打开 `诊断报告.txt`，包含：

1. 当前时间
2. 定时任务是否存在
3. 任务详细配置（触发时间、上次运行时间、上次结果码、下次运行时间）
4. `output\logs` 目录内容
5. 任务入口控制台日志
6. 最新结果文件及修改时间
